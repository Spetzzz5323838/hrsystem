# Переведення, компетенції, заморозка, відпустки — проєктні рішення v1.2

---

## 1. Компетенції замість «пройшов онбординг»

Три ваші вимоги — не вчити повторно після повернення, підтягувати різницю при зміні посади, не вчити те саме двічі — це одна задача. Вона не вирішується правилом «менше 12 місяців і та сама посада»: воно не покриває перехід продавця в касири й не враховує, що санітарія застаріває швидше за знання структури компанії.

**Рішення: облік ведеться не по трекам навчання, а по компетенціях.**

```prisma
model Competency {
  id Int @id @default(autoincrement())
  code String @unique
  name String
  validMonths Int?            // null = безстроково
  resetOnBreakMonths Int?     // обнулити, якщо перерва в роботі довша
  isBonus Boolean @default(false)
}

model PositionCompetency {     // що вимагає профіль посади
  positionProfileId Int
  competencyId Int
  @@id([positionProfileId, competencyId])
}

model CompetencyRecord {       // що людина має
  id Int @id @default(autoincrement())
  personId Int
  competencyId Int
  passedAt DateTime
  score Int?
  validUntil DateTime?
  source CompetencySource      // ATTESTATION | TEST | EXTERNAL_COURSE | MANUAL
  frozenDays Int @default(0)   // пауза годинника під час заморозки
}
```

**Єдина формула, з якої випливають усі три сценарії:**

```
дельта = компетенції_посади − чинні_компетенції_людини
```

| Ситуація | Дельта | Що отримує працівник |
|---|---|---|
| Новий касир | усі 8 | повний трек |
| Повернувся касиром через 4 місяці | порожня | тільки документи й 1С, навчання немає |
| Повернувся касиром через 2 роки | санітарія, ОП, ПБ (строк вийшов) | короткий трек із 3 позицій |
| Продавець → касир | каса і ПРРО | одна компетенція плюс атестація по ній |
| Касир → пекар | технологія, обладнання цеху | дві компетенції |
| Пекар → адміністратор | каса, стандарти, матвідповідальність | трек підвищення кваліфікації |

Правило «12 місяців» з v1.0 скасовується. Його роль перебирає `validMonths` на кожній компетенції окремо — це точніше і не потребує винятків.

**Стартові строки дії:**

| Компетенція | Строк | Обнулення при перерві |
|---|---|---|
| Компанія і структура | безстроково | 12 міс |
| Охорона праці | 12 міс | — |
| Пожежна безпека | 12 міс | — |
| Санітарія і HACCP | 12 міс | — |
| Стандарти обслуговування | 24 міс | 18 міс |
| Каса і ПРРО | 24 міс | 12 міс |
| Ваговий товар і терміни | 24 міс | 18 міс |
| Матвідповідальність | 24 міс | 12 міс |
| Технологія випічки | 24 міс | 18 міс |
| Обладнання цеху | 24 міс | 12 міс |
| Безпека дорожнього руху | 12 міс | — |
| Правила торгівлі (бонус) | 12 міс | — |

Побічний ефект, який виявиться цінним: система сама покаже, у кого в магазині завтра «протухає» санітарія чи охорона праці, і поставить задачу на переатестацію до того, як це знайде перевірка.

## 2. Переведення

### 2.1 Хто погоджує

Ви сформулювали: ініціює безпосередній керівник або вище, погоджує директор кластера або вище. Формалізую так, щоб працювало й для переходів між кластерами:

```
погоджувач = керівник найближчого спільного вузла рівня DIVISION,
             що охоплює і старе, і нове місце роботи
```

| Переведення | Спільний вузол | Погоджує |
|---|---|---|
| Каса → Гастрономія в межах SH01 | Кластер 1 | директор кластера |
| SH01 → SH03 (той самий кластер) | Кластер 1 | директор кластера |
| SH01 → SH04 (інший кластер) | Роздріб → Компанія | COO |
| Магазин → Пекарський цех | Компанія | COO |

Правило одне, винятків не потрібно. Якщо захочете, щоб переведення всередині одного об'єкта погоджував сам адміністратор — це рядок у налаштуваннях, а не зміна логіки.

### 2.2 Чек-ліст переведення

| # | Пункт | Відповідальний | Блок. | Умова |
|---|---|---|---|---|
| 1 | Ініціація: нове місце, посада, дата | Керівник | ✅ | |
| 2 | Погодження переведення | Директор кластера або вище | ✅ | |
| 3 | Передача ТМЦ і зняття обладнання | Ревізор | ✅ | якщо МВО |
| 4 | Зміна доступів у 1С, перереєстрація на касі | Оператор 1С | ✅ | |
| 5 | Кадрове оформлення переведення | Бухгалтер | ✅ | |
| 6 | Дельта-навчання за новим профілем | Куратор | ✅ | якщо дельта не порожня |
| 7 | Атестація за новим профілем | Адміністратор нового місця | ✅ | якщо дельта не порожня |
| 8 | Закріплення обладнання на новому місці | Адміністратор | | |
| 9 | Оновлення штатного розпису обох вузлів | Система | ✅ | |

Статус на час процедури — `TRANSFER_PENDING`. Працівник продовжує працювати на старому місці, доки пункт 5 не закрито.

## 3. Заморозка

Заморозка — не відпустка. Це довга пауза без звільнення: декрет, мобілізація, тривале лікування, навчання, сезонна перерва.

| Аспект | Рішення |
|---|---|
| Статус | `FROZEN`, з причиною з довідника і планованою датою повернення |
| Штатний розпис | позиція лишається зайнятою або звільняється — вибір при заморозці, бо для декрету беруть заміну, а для місячної паузи ні |
| Обладнання | питання на екрані заморозки: здати чи лишити за працівником |
| Доступи 1С | блокуються, але не видаляються |
| **Компетенції** | **годинник строку дії зупиняється** — `frozenDays` накопичується і додається до `validUntil` при розморозці |
| Повернення | перерахунок дельти на дату виходу; якщо дельта порожня — одразу в роботу |
| Нагадування | за 14 днів до планованої дати повернення — адміністратору й бухгалтеру |

Зупинка годинника компетенцій — принципова деталь. Інакше людина після року декрету виходить із повністю простроченим профілем і мусить перескладати все, включно з тим, що не встигло застаріти по суті.

## 4. Відпустки

### 4.1 Процес

1. Працівник подає заяву в Telegram: тип, дати. Або адміністратор подає за нього у веб.
2. Система перевіряє конфлікти й показує їх ініціатору **до** відправлення.
3. Погоджує безпосередній керівник. Якщо заявка довша за 14 днів або конфліктує — піднімається на рівень вище.
4. Після погодження дати потрапляють у календар об'єкта, працівник отримує підтвердження в Telegram.

### 4.2 Контроль конфліктів

| Правило | Реакція |
|---|---|
| Одночасно відсутні більше 30% штатних одиниць посади у відділі | попередження ініціатору, погодження тільки рівнем вище |
| Відсутні всі працівники критичної посади (єдиний адміністратор, єдиний водій) | блокування, потрібне погодження COO |
| Перетин із періодом інвентаризації або пікового сезону | попередження з назвою події |
| Заявка менше ніж за 14 днів до початку | позначка «поза графіком», погодження рівнем вище |

### 4.3 Межа компетенції системи

Залишок днів відпустки — це кадровий облік, якого в системі поки немає. До появи кадрового модуля залишок вводить бухгалтер вручну як довідкове поле, а система рахує тільки використані дні за своїми записами. Обіцяти точний баланс без кадрового модуля не можна — там стаж, переведення, компенсації й невикористані дні за попередні роки.

## 5. Номер телефону як ідентифікатор

Тут я не погоджуся з постановкою в чистому вигляді.

Телефон — відмінний **природний ключ для входу й пошуку**: людина його пам'ятає, Telegram передає його при реєстрації через кнопку «Поділитися контактом», звірка автоматична. Але як **первинний ключ** він не годиться:

- номер змінюється, а всі зв'язки в базі при цьому мають вижити;
- оператори повторно продають номери через 6–12 місяців неактивності;
- у людини може бути два номери, і на другий вона напише в бот.

**Рішення:** внутрішній `id` лишається первинним ключем. Телефон — унікальне поле з історією змін:

```prisma
model Person {
  id Int @id @default(autoincrement())
  phone String @unique          // +380XXXXXXXXX, нормалізований формат
  phoneVerifiedAt DateTime?     // підтверджено через Telegram contact
  telegramId BigInt? @unique
}

model PhoneHistory {
  id Int @id @default(autoincrement())
  personId Int
  phone String
  from DateTime
  to DateTime?
}
```

Пошук по телефону працює як ви й хотіли: бухгалтер вводить номер — знаходить людину, навіть якщо вона звільнялася двічі. При повторному найомі система сама пропонує: «Цей номер уже є в базі: Іваненко І.І., касир, звільнений 10.04.2026. Прийняти цю людину?» — і підтягує компетенції.

## 6. Що додається в картку працівника

| Поле | Деталі |
|---|---|
| Фотографія | завантаження з веб-камери або файлом; для бейджа й швидкого впізнавання |
| Телефон | з позначкою підтвердження через Telegram |
| Компетенції | таблиця: потрібно за посадою · є · дійсна до · статус |
| Історія профілю | усі зміни: посада, відділ, статус, куратор, телефон, оцінки — з датою й автором |

Історія профілю — це фільтр по `AuditLog` за конкретним працівником. Технічно нічого нового не потрібно, `AuditLog` уже в моделі з v1.0.

## 7. Нові довідники

Три екрани, яких бракувало в прототипі:

1. **Профілі посад** — картка з рівнем, прапорцями (каса, МВО, харчове), переліком компетенцій, документів і модулів чек-ліста. Створення й редагування.
2. **Компетенції** — назва, строк дії, обнулення при перерві, бонусна чи обов'язкова, прив'язані матеріали й тест.
3. **Матеріали** — PDF або відео, посилання на intranet, прапорець «надсилати ботом», прив'язка до компетенції.

Логіка зв'язку: посада вимагає компетенції → компетенція має матеріали й тест → успішний тест створює `CompetencyRecord` зі строком дії. Навчальний профіль посади не редагується окремо — він збирається автоматично з компетенцій.
