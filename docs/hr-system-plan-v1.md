# Система onboarding / offboarding персоналу — технічний план v1.0

Консолідована версія. Замінює v0.1 і v0.2 — усі відкриті питання закриті.

**Стек:** PostgreSQL · Prisma · Node.js (Fastify) · React + Vite + TypeScript · Telegram Bot API (grammY) · pg-boss
**Контур:** локальна мережа, магазини через VPN, публічного доступу немає

---

## 1. Межі системи

**Входить:** прийом, адаптація, навчання, тестування, атестація, профіль працівника, рейтинг, закріплення обладнання, звільнення з узгодженням, оргструктура, сповіщення.

**Не входить:** кадрове діловодство (накази, трудові книжки, ЄСВ), нарахування зарплати, табелювання, інтеграція з 1С. Система працює **без юридичної прив'язки** — усі документи, що мають юридичну силу, оформлює бухгалтер поза системою. Система дає бухгалтеру підставу й підтвердження, що процедуру пройдено.

## 2. Масштаб

| Показник | Значення |
|---|---|
| Об'єкти зараз | 6 магазинів + 1 виробництво = 7 |
| Плануються | +2 магазини найближчим часом → 9 |
| Одночасні користувачі веб | орієнтовно 15–30 |
| Працівників у системі | *потребує уточнення — оцінка 250–400* |
| Нових прийомів на місяць | *потребує уточнення — від цього залежить лише навантаження на сповіщення* |

На цьому масштабі архітектурних ускладнень не потрібно: один процес Node, одна база, черга на PostgreSQL. Шардинг, Redis, мікросервіси — зайві.

**Наслідок від «+2 магазини»:** шаблони об'єктів (п.5.5) потрібні вже в першому релізі, не потім.

## 3. Розгортання

### 3.1 Топологія

```
                          Інтернет
                              │ тільки вихідні (long polling)
                              ▼
                      api.telegram.org
                              ▲
┌──────────── Windows Server 2019 (ЦО) ───────────┐
│  PostgreSQL 16                                   │
│  Node.js-сервіс (Windows Service через NSSM):    │
│    ├── Fastify: REST API + віддача SPA           │
│    ├── grammY: Telegram-бот (long polling)       │
│    ├── pg-boss: черга, SLA-ескалації, нагадування│
│    └── Puppeteer: генерація PDF                  │
│  D:\hr-docs — скани документів                   │
└──────┬──────────────────────┬────────────────────┘
       │ VPN                  │ LAN
  6+2 магазини          Виробництво, бухгалтерія,
  (браузер, планшет)     ревізор, COO, ІТ
```

### 3.2 Ресурси

| Компонент | Оцінка |
|---|---|
| RAM | 8 ГБ виділено під стек (Node ~1 ГБ, Puppeteer до 500 МБ на рендер, PostgreSQL 2–4 ГБ) |
| CPU | 4 vCPU |
| Диск під БД | 20 ГБ (зростання повільне) |
| Диск під скани | 50–100 ГБ (5–7 сканів × 400 працівників × ~3 МБ, з запасом) |
| Порти | 443 у LAN (самопідписаний або внутрішній CA), 5432 — тільки localhost |

### 3.3 Ризик спільного сервера

Якщо цей Windows Server 2019 — той самий, де живуть MS SQL з базою 1С і термінальний сервер, то Node + Puppeteer + PostgreSQL конкуруватимуть за пам'ять і диск з продуктивом 1С. Термінальні сесії 1С чутливі до дискових затримок.

**Заходи:**
1. Уточнити, чи це окремий фізичний/віртуальний сервер (див. п.19, задача ІТ-1).
2. Якщо спільний — виносити стек у окрему віртуалку Hyper-V з жорсткими лімітами RAM і CPU.
3. Генерацію PDF винести в чергу з обмеженням `teamConcurrency: 1` — щоб Puppeteer ніколи не стартував у кількох екземплярах.
4. `shared_buffers` PostgreSQL обмежити явно, не лишати за замовчуванням.
5. Бекап робити не в години пікового навантаження 1С.

### 4.2 Модель доступу

```prisma
model RoleAssignment {
  id         Int  @id @default(autoincrement())
  employeeId Int
  role       Role
  orgNodeId  Int                 // вузол; доступ поширюється на все піддерево
  createdAt  DateTime @default(now())
  createdById Int
  @@unique([employeeId, role, orgNodeId])
}
```

Правило перевірки одне: `target.orgNode.path` починається з `scope.orgNode.path`. Для бухгалтера, оператора 1С, ревізора і COO `orgNodeId` = корінь.

Одна людина може мати кілька призначень (адміністратор двох магазинів під час підміни) — модель це підтримує.

### 4.4 Автентифікація

| Аспект | Рішення |
|---|---|
| Облікові записи | локальні: `login` + argon2id-хеш, прив'язані до `Employee` |
| Створення | автоматично при призначенні ролі рівня ≥ 30 або функціональної; одноразове посилання на встановлення пароля — у Telegram |
| Сесії | httpOnly + SameSite=Strict cookie, TTL 12 год, «довірений пристрій» 30 днів |
| 2FA | опційно для `ONEC_ADMIN`, `ACCOUNTANT`, `COO`, `SYSADMIN`: підтвердження входу кнопкою в Telegram |
| Відновлення пароля | через бота, без email |
| Блокування | при `TERMINATION_STARTED` — автоматичне зняття всіх `RoleAssignment` і активних сесій |
| AD/LDAP | не в MVP; шар провайдерів спроєктувати так, щоб додати без міграції |

## 5. Оргструктура

### 5.1 Модель

```prisma
model OrgNode {
  id             Int @id @default(autoincrement())
  type           OrgNodeType
  name           String
  code           String? @unique          // SH01, TSEH, WH1
  parentId       Int?
  path           String                   // матеріалізований шлях '1.3.14.52'
  headEmployeeId Int?
  address        String?
  isActive       Boolean @default(true)
  sortOrder      Int @default(0)
  @@index([path])
}

enum OrgNodeType { COMPANY DIVISION OBJECT DEPARTMENT }
```

### 5.2 Дерево

```
Компанія
├── Роздріб (DIVISION)
│   ├── SH01 Коровай Шаргород (OBJECT) → Каса, Гастрономія, Бакалія, Кулінарія
│   ├── SH02 … SH06 (OBJECT)
│   └── [SH07, SH08 — плануються]
├── Виробництво (DIVISION)
│   ├── TSEH Пекарський цех (OBJECT) → Зміна А, Зміна Б
│   └── WH1 Склад (OBJECT)
└── Адміністрація (DIVISION)
    ├── Бухгалтерія
    ├── ІТ / 1С
    └── Ревізійна служба
```

### 5.3 Посади: каталог окремо від штатних одиниць

```prisma
model PositionProfile {                  // глобальний каталог
  id Int @id @default(autoincrement())
  title String
  level Int
  canBeCurator Boolean @default(false)
  requiresCashierAccount Boolean @default(false)
  onboardingTemplateId Int?
  offboardingTemplateId Int?
  isActive Boolean @default(true)
}

model StaffUnit {                        // штатна одиниця у вузлі
  id Int @id @default(autoincrement())
  positionProfileId Int
  orgNodeId Int
  plannedHeadcount Int @default(1)
  @@unique([positionProfileId, orgNodeId])
}
```

Профіль «Касир» описується один раз — з треком онбордингу, матеріалами й переліком документів — і розставляється по всіх дев'яти об'єктах. Звідси безкоштовно: вакансії (`plannedHeadcount` − факт), укомплектованість, звіт «де бракує людей».

### 5.4 Рівні посад

| Рівень | Хто | Права |
|---|---|---|
| 10 | касир, продавець, пекар, комірник | свій профіль |
| 20 | старший зміни, бригадир | + своя зміна |
| 30 | адміністратор магазину, начальник цеху | активація, атестація, ініціація звільнення, рейтинг |
| 40 | керівник напрямку, супервайзер | усі об'єкти напряму |
| 50 | COO | уся компанія, аналітика |
| 60 | власник | усе + аудит-лог |

Атестацію приймає той, у кого `level ≥ 30` **і** чия область покриває вузол працівника. «Вищий по посаді» резолвиться підйомом по дереву через `headEmployeeId`.

Бухгалтер, оператор 1С і ревізор у цю шкалу не входять — їхні повноваження задаються `RoleAssignment`, а не рівнем.

### 5.5 Інтерфейс і шаблони об'єктів

Двопанельний екран: зліва дерево з drag & drop, справа картка вузла з вкладками «Загальне / Штатний розпис / Працівники / Обладнання / Доступи / Історія».

Обов'язково в першому релізі:

1. **«Створити об'єкт за шаблоном»** — набір відділів + штатний розпис копіюється одним кліком. При двох магазинах на підході це не опція, а вимога.
2. Перерахунок `path` при переміщенні вузла — в одній транзакції.
3. Архівація замість видалення (`isActive = false`) — історія працівників не ламається при закритті об'єкта.
4. Заборона видалення вузла з активними працівниками.
5. Масове переведення працівників між вузлами.
6. Історія змін структури в `AuditLog`.

## 6. Рушій процесів і задач

Onboarding і звільнення **не програмуються** як окремі пайплайни. Обидва — конфігуровані шаблони.

```prisma
model ProcessTemplate {
  id Int @id @default(autoincrement())
  type ProcessType                     // ONBOARDING | OFFBOARDING | EXTRA_TRAINING
  name String
  items ChecklistItemTemplate[]
}

model ChecklistItemTemplate {
  id Int @id @default(autoincrement())
  templateId Int
  order Int
  title String
  responsibleRole Role
  actionType ActionType                // MARK | UPLOAD | INPUT_VALUE | TEST | APPROVAL
  isBlocking Boolean @default(true)
  slaHours Int?
  dependsOnItemId Int?
}

model ProcessInstance {
  id Int @id @default(autoincrement())
  employeeId Int
  templateId Int
  state ProcessState                   // RUNNING | DONE | CANCELLED
  startedAt DateTime @default(now())
  finishedAt DateTime?
  tasks Task[]
}

model Task {
  id Int @id @default(autoincrement())
  instanceId Int
  itemTemplateId Int
  assigneeId Int?                      // резолвиться (роль + область)
  status TaskStatus                    // PENDING | BLOCKED | DONE | OVERDUE
  payload Json?
  comment String?
  dueAt DateTime?
  completedAt DateTime?
  completedById Int?
}
```

Додати крок «отримати спецодяг» для профілю «Пекар» = один рядок у довіднику, без релізу.

| # | Подія | Отримувач | Дія |
|---|---|---|---|
| 1 | Реєстрація по QR (ПІБ, дата народження) | STORE_ADMIN об'єкта | «Заповнити профіль» → веб |
| 2 | Активація профілю | Куратор | чек-ліст навчання підопічного |

| 4 | Активація профілю | ONEC_ADMIN | «Зареєструвати в 1С + касу» |
| 5 | Активація профілю | ACCOUNTANT | «Оформити, зібрати документи» |
| 6 | 1С видав пароль | Працівник | штрихкод, одноразово |
| 7 | Бухгалтер закрив оформлення | STORE_ADMIN, Куратор | «Може приступати до навчання» |
| 8 | Куратор закрив стажування | Працівник | кнопка «Готовий до атестації» |
| 9 | Працівник натиснув кнопку | STORE_ADMIN | чек-ліст атестації + PDF на друк |
| 10 | Атестацію складено | Працівник, Куратор, COO | статус ACTIVE |

Шаблони повідомлень — у БД (`NotificationTemplate`), не в коді. Кожне відправлення пишеться в `Notification` зі статусом, ретраї через pg-boss.

**Пароль з 1С:** шифрування AES-256-GCM (ключ у змінних середовища, не в БД), штрихкод Code128 генерується на льоту через `bwip-js`, повідомлення з `protect_content: true`, кожен показ у `AuditLog`, перевидача — тільки `ONEC_ADMIN`.

## 9. Навчання і LMS

### 9.1 Розподіл каналів (рішення по п.6 попередньої версії)

Wi-Fi покриває 90% площі магазинів → варіант з intranet життєздатний.

| Тип матеріалу | Канал | Доступність |
|---|---|---|
| PDF, регламенти, welcomebook | файлом прямо в Telegram (Bot API до 50 МБ) | будь-де, у т.ч. вдома |
| Відео | посилання на intranet | у магазині через Wi-Fi або з робочого ПК |
| Тести | бот (прості) або веб (розгорнуті) | будь-де |

**Задача ІТ (див. п.19):** гостьова/персонал-мережа Wi-Fi має мати маршрут **тільки до хоста LMS** по 80/443, а не до серверного сегмента. Окремий SSID або VLAN з ACL. Без цього телефони персоналу отримають доступ до всієї мережі.

Дублювання PDF у бот закриває 10% «мертвих зон» і випадки, коли людина хоче почитати вдома.

### 9.2 Модель

| Сутність | Ключові поля |
|---|---|
| `Material` | `type` (PDF/VIDEO/LINK), `url` або `filePath`, `durationMin`, `sendViaBot` |
| `PositionMaterial` | `materialId`, `positionProfileId`, `isMandatory` |
| `MaterialView` | факт відкриття: `employeeId`, `materialId`, `openedAt` |
| `Test` / `Question` / `Option` | `passScore`, `attemptsAllowed`, `isBonus` |
| `TestAttempt` | `score`, `passed`, `answers Json`, `startedAt`, `finishedAt` |

Додаткові навчання (пожежна безпека, правила торгівлі) — `isBonus = true`: не входять у мінімальний набір, успішна здача дає бали рейтингу.

## 10. Рейтинг

`ratingScore` = сума `RatingEvent.points` за останні 12 місяців; повна історія доступна окремо.

| Подія | Бали |

| Негатив | −5 |
| Догана (тільки COO) | −20 |

## 12. Процес звільнення

### 12.1 Послідовність і гейти

```
STORE_ADMIN ініціює у профілі працівника
        │  статус → TERMINATION_STARTED
        │  запуск ProcessInstance(OFFBOARDING)
        ▼
┌───────────────── паралельні задачі ─────────────────┐
│ ONEC_ADMIN: блокування облікових записів, каса      │
│ AUDITOR: квитування обладнання по списку            │
│ STORE_ADMIN: повернення ключів, бейджа, спецодягу   │
└──────────────────────┬──────────────────────────────┘
                       │ усі блокуючі DONE
                       ▼
                COO: погодження
                       │
                       ▼
        ACCOUNTANT: сповіщення «можна розраховувати»
                       │
                       ▼
    Друк листа узгодження → закриття → TERMINATED
```

Бухгалтер оформлює звільнення юридично поза системою. Система дає йому статус і документ-підставу.

### 12.2 Лист узгодження звільнення

Замість розрахункового листка (рішення по п.4). Не документ строгої звітності — внутрішній обхідний лист.

```prisma
model ClearanceSheet {
  id Int @id @default(autoincrement())
  number String @unique                // ЗВ-2026-0042
  employeeId Int
  instanceId Int                       // ProcessInstance(OFFBOARDING)
  generatedById Int
  generatedAt DateTime @default(now())
  isComplete Boolean                   // усі блокуючі пункти закрито
  pdfPath String
  hash String                          // SHA-256 змісту для звірки
}
```

**Склад документа:**

| Блок | Зміст |
|---|---|
| Шапка | номер, ПІБ, посада, об'єкт, дата прийому, дата ініціації, ініціатор |
| Таблиця пунктів | пункт · відповідальний (ПІБ) · статус · дата й час · коментар |
| Обладнання | перелік закріплених позицій із результатом квитування ревізора |
| Підсумок | «Усі обов'язкові пункти закрито» або перелік незакритих |
| Футер | хто і коли сформував, хеш для звірки |

Кнопка друку доступна завжди; якщо не всі блокуючі пункти закрито — PDF формується з позначкою «ПОПЕРЕДНІЙ, процедуру не завершено». Це дозволяє бухгалтеру бачити стан у будь-який момент, але не дає видати остаточний документ передчасно.

Статуси бухгалтер у будь-якому разі бачить наживо в програмі — документ потрібен для паперового архіву й підпису.

## 13. Повторний найм

```
якщо (дата звільнення в межах 12 місяців) І (та сама PositionProfile):
    → ProcessTemplate(ONBOARDING) не запускається
    → створюються тільки задачі ONEC_ADMIN і ACCOUNTANT
    → статус одразу ACTIVE
    → рейтинг, історія тестів і атестацій зберігаються
```

`RatingEvent`, `TestAttempt` і `EmploymentPeriod` при звільненні не видаляються — це і є накопичена цінність системи.

## 15. Адміністрування (SYSADMIN)

| Може | Не може |
|---|---|
| Довідники: посади, відділи, типи документів, обладнання | Переглядати скани документів |
| Шаблони процесів і чек-лістів | Приймати атестацію |
| Шаблони сповіщень | Ставити рейтингові оцінки |
| Ваги рейтингу | Погоджувати звільнення |
| LMS: матеріали, тести | Змінювати статуси працівників вручну |
| Оргструктура | Видаляти записи `AuditLog` |
| Перегляд аудит-логу | |

Усі дії `SYSADMIN` логуються без винятків. Ручна зміна статусу працівника заборонена принципово — статус має бути наслідком процесу, інакше система перестає відображати реальність.
