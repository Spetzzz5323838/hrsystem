# Довідники, права доступу та чек-лісти — v1.1

Доповнення до технічного плану v1.0. Усе нижче — **стартове наповнення**, яке завантажується сідами при розгортанні і далі редагується через інтерфейс без участі розробника.

## 1. Оновлення після ваших рішень

| Рішення | Наслідок |
|---|---|
| Сервер окремий, ресурсів достатньо | Задача ІТ-1 знята. Puppeteer і pg-boss без обмежень concurrency |
| Кадрове діловодство і зарплата — наступний етап | Модель даних треба готувати зараз, див. п.1.1 |
| З'явилася посада «Директор кластера» | В оргструктуру додається рівень CLUSTER, див. п.2 |
| Профілі посад мають створюватись і редагуватись | Каталог посад — повноцінний CRUD, а не константи в коді |
| Ієрархія налаштовується | Права описуються як матриця «можливість × область», див. п.4 |

### 1.1 Що закласти зараз під майбутнє кадрове діловодство

Це коштує кілька годин зараз і кілька тижнів переробки потім.

1. **Розділити `Person` і `Employment`.** Зараз усе в `Employee`. Правильно: `Person` (фізособа: ПІБ, дата народження, документи, telegramId) і `Employment` (факт роботи: посада, об'єкт, дати, ставка). Одна людина — багато періодів роботи, а при кадровому обліку ще й кілька одночасних (сумісництво, підміна в іншому магазині).
2. **`externalRef` на всіх ключових сутностях** (`Person`, `OrgNode`, `PositionProfile`) — порожнє поле під майбутній ідентифікатор 1С. Додати пізніше = міграція з ручним зіставленням сотень записів.
3. **Не змішувати посаду і штатну одиницю** — вже враховано в v1.0 (`PositionProfile` / `StaffUnit`). Для штатного розпису й зарплати це база.
4. **Довідник причин звільнення** з кодом — зараз використовується як текст, потім мапиться на статті КЗпП.
5. **Календар робочого часу об'єкта** (графіки змін) — не реалізовувати, але передбачити зв'язок `StaffUnit → ShiftPattern`.

## 2. Оргструктура з кластерами

Посада «Директор кластера» вимагає проміжного рівня між напрямом і об'єктом:

```
Компанія
├── Роздріб (DIVISION)
│   ├── Кластер 1 (DIVISION) ← директор кластера
│   │   ├── SH01 Коровай Шаргород (OBJECT)
│   │   ├── SH02 (OBJECT)
│   │   └── SH03 (OBJECT)
│   └── Кластер 2 (DIVISION)
│       ├── SH04, SH05, SH06
│       └── [SH07, SH08 — плануються]
├── Виробництво (DIVISION)
│   ├── TSEH Пекарський цех → Зміна А, Зміна Б
│   ├── Кулінарія
│   ├── М'ясний цех
│   └── WH1 Склад
└── Адміністрація (DIVISION)
    ├── Бухгалтерія
    ├── ІТ / 1С
    ├── Ревізійна служба
    ├── Комерційний відділ (категорійні менеджери, маркетинг)
    └── Транспорт
```

Тип `DIVISION` навмисно універсальний — кластер, напрям і відділ офісу описуються ним же. Додавати окремий тип `CLUSTER` не треба: це створить жорсткість там, де завтра захочеться перегрупувати.

## 4. Модель прав: «можливість × область»

Ваша вимога — «начальник бачить усе в межах свого відділу, підлеглий тільки себе, ієрархія налаштовується». Реалізується трьома сутностями.

### 4.1 Області дії

| Область | Що охоплює |
|---|---|
| `SELF` | тільки власний профіль |
| `SUBORDINATES` | прямі підлеглі (за `managerId`) |
| `OWN_DEPARTMENT` | свій відділ (вузол DEPARTMENT) |
| `OWN_OBJECT` | свій об'єкт цілком, усі відділи |
| `OWN_SUBTREE` | свій вузол і все нижче — для директора кластера |
| `CUSTOM_NODE` | явно вказаний вузол — для підмін і суміщення |
| `COMPANY` | уся компанія — бухгалтер, 1С, ревізор, COO |

### 4.2 Можливості (capabilities)

```
VIEW_EMPLOYEE          EDIT_PROFILE           ACTIVATE_EMPLOYEE
ASSIGN_CURATOR         VIEW_DOCUMENTS         UPLOAD_DOCUMENTS
SET_1C_PASSWORD        CLOSE_INTERNSHIP       RUN_ATTESTATION
RATE_POSITIVE_NEGATIVE ISSUE_REPRIMAND_AWARD  ASSIGN_EQUIPMENT
CLEAR_EQUIPMENT        INIT_TERMINATION       APPROVE_TERMINATION
CLOSE_TERMINATION      PRINT_CLEARANCE        MANAGE_MATERIALS
MANAGE_TEMPLATES       MANAGE_ORG_STRUCTURE   VIEW_ANALYTICS
VIEW_AUDIT_LOG         MANAGE_REMINDERS
```

### 4.3 Модель

```prisma
model PermissionGrant {
  id                Int @id @default(autoincrement())
  positionProfileId Int?              // грант через посаду
  role              Role?             // або через функціональну роль
  capability        Capability
  scope             ScopeType
  customNodeId      Int?              // тільки для CUSTOM_NODE
  @@index([positionProfileId])
}

model Employee {
  // ...
  managerId Int?                      // пряма підлеглість
}
```

**Ефективні права** = об'єднання грантів від профілю посади і від усіх `RoleAssignment`, з найширшою областю. Перевірка одна: `target.orgNode.path` починається з `resolvedScope.path`.

`managerId` за замовчуванням підтягується з `OrgNode.headEmployeeId` вузла працівника, але перевизначається вручну — це і є «підлеглість налаштовується». Потрібно для випадків, коли людина працює в одному відділі, а підпорядковується керівнику іншого.

### 4.4 Стартова матриця

| Профіль | Можливості (область) |
|---|---|
| Лінійний персонал (10) | `VIEW_EMPLOYEE(SELF)` |
| Кваліфікований (15) | `VIEW_EMPLOYEE(SELF)` |
| Старший зміни (20) | `VIEW_EMPLOYEE(OWN_DEPARTMENT)`, `CLOSE_INTERNSHIP(SUBORDINATES)`, `RATE(SUBORDINATES)` |
| Адміністратор магазину (30) | усе по `OWN_OBJECT`: `VIEW`, `EDIT_PROFILE`, `ACTIVATE`, `ASSIGN_CURATOR`, `UPLOAD_DOCUMENTS`, `RUN_ATTESTATION`, `RATE`, `ASSIGN_EQUIPMENT`, `INIT_TERMINATION`, `PRINT_CLEARANCE`, `MANAGE_MATERIALS`, `MANAGE_REMINDERS` |
| Завідуючий цехом (30) | те саме по своєму цеху |
| Директор кластера (40) | те саме по `OWN_SUBTREE` + `VIEW_ANALYTICS(OWN_SUBTREE)` |
| Категорійний менеджер (40) | `VIEW_EMPLOYEE(SUBORDINATES)`, `RATE(SUBORDINATES)`, `VIEW_ANALYTICS(COMPANY)` |
| Бухгалтер | `VIEW_EMPLOYEE(COMPANY)`, `VIEW_DOCUMENTS(COMPANY)`, `UPLOAD_DOCUMENTS(COMPANY)`, `CLOSE_TERMINATION`, `PRINT_CLEARANCE`, `MANAGE_REMINDERS` |
| Бухгалтер-ревізор | `VIEW_EMPLOYEE(COMPANY)`, `CLEAR_EQUIPMENT(COMPANY)`, `ASSIGN_EQUIPMENT(COMPANY)` |
| Оператор 1С | `VIEW_EMPLOYEE(COMPANY)`, `SET_1C_PASSWORD(COMPANY)` |
| Системний адміністратор | `MANAGE_TEMPLATES`, `MANAGE_ORG_STRUCTURE`, `MANAGE_MATERIALS`, `VIEW_AUDIT_LOG`. **Без** `VIEW_DOCUMENTS` |
| Фінансовий директор / Власник | усе по `COMPANY`, включно з `APPROVE_TERMINATION`, `ISSUE_REPRIMAND_AWARD`, `VIEW_AUDIT_LOG` |

### 4.5 Інтерфейс налаштування

Екран «Права доступу»: таблиця, де рядки — можливості, стовпці — профілі посад, у клітинці — випадаючий список областей. Зверху перемикач «Профілі посад / Функціональні ролі». Внизу — кнопка «Симуляція»: обрати працівника і побачити, що саме він бачить і може. Це критично: матриця на 22 можливості × 30 посад без симулятора не налагоджується.

Будь-яка зміна прав пише в `AuditLog` із diff.

Трек працівника = базовий шаблон + усі модулі, що підходять за прапорцями профілю посади. Наприклад, старший касир: базовий + Касовий + МВО + Харчове + Роздріб.

### 6.3 Скорочений трек для повторного найму

Якщо пауза менше 12 місяців і та сама посада — виконуються тільки пункти 3, 5, 6, 7 і модульні пункти, пов'язані з документами. Навчання, стажування й атестація пропускаються.

## 9. Версіонування шаблонів

Технічна деталь, яку легко пропустити і дорого виправляти.

```prisma
model ProcessTemplate {
  id Int @id @default(autoincrement())
  code String                          // ONBOARDING_BASE
  version Int
  isActive Boolean
  @@unique([code, version])
}
```

`ProcessInstance` фіксує конкретну версію шаблону. Редагування шаблону створює нову версію; процеси, що вже виконуються, доживають на старій. Інакше зміна чек-ліста в середу зламає всі відкриті онбординги і задачі почнуть зникати в людей з-під рук.

Те саме для `AttestationTemplate` — результат атестації має посилатися на версію чек-ліста, за якою її приймали.
