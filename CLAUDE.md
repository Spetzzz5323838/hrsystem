# HR-система: onboarding, навчання, рух і звільнення персоналу

## Про проєкт

Внутрішня система управління персоналом для мережі продуктових магазинів «Коровай» і виробництва у Вінницькій області. 7 об'єктів (6 магазинів + пекарський цех і склад), найближчим часом +2 магазини.

Система закриває: прийом працівника, оформлення документів, навчання й атестацію, оцінювання, переведення між об'єктами, заморозку, відпустки, звільнення з узгодженням.

**Не входить у систему:** кадрове діловодство (накази, трудові книжки, ЄСВ), нарахування зарплати, інтеграція з 1С. Це наступний етап. Але модель даних має бути до цього готова.

**Облік робочого часу — входить** (рішення власника 2026-10-18, змінює початкове): фактичні прибуття/завершення зміни через термінал зі сканером бейджа, без планового графіка й без перерв. Код працівника генерує сама система (не 1С).

## Мова

Спілкування, коментарі в коді, назви в інтерфейсі, повідомлення про помилки для користувача — **українською**. Назви змінних, таблиць і файлів — англійською.

## Prisma 7: критично важливо

Більшість інструкцій в інтернеті написані для Prisma 6 і тут не працюють.

- Використовується адаптер `PrismaPg` + `pg.Pool`
- Поля `url` у `schema.prisma` **немає** — з'єднання налаштовується в коді
- Обов'язковий файл `prisma.config.ts`
- Потрібні пакети: `@prisma/adapter-pg`, `pg`
- Prisma Studio запускається тільки так: `npx dotenv -e .env -- npx prisma studio`
- Seed-скрипти потребують `dotenv`, іноді з приведенням типу `as any`
- Dev-сервер: `npx dotenv -e .env -- npx next dev`

Якщо міграція падає з помилкою про доступ до схеми `public` — потрібно `GRANT ALL ON SCHEMA public TO hruser;` усередині бази `hrsystem`.

## Ключові архітектурні рішення

Ці рішення прийняті й обговоренню не підлягають без явної вказівки.

1. **Два інтерфейси.** Веб у локальній мережі — для адміністраторів, бухгалтерії, оператора 1С, ревізора, керівництва. Telegram — для лінійного персоналу. Публічного доступу з інтернету немає, бот працює на long polling.

2. **Оргструктура — єдине дерево** типізованих вузлів (COMPANY / DIVISION / OBJECT / DEPARTMENT) з матеріалізованим шляхом `path` виду `1.2.3.4`. Перевірка доступу зводиться до `target.path.startsWith(scope.path)`.

3. **Посада ≠ штатна одиниця.** `PositionProfile` — глобальний каталог. `StaffUnit` — посада в конкретному вузлі. Працівник кріпиться до `StaffUnit`.

4. **Права = можливість × область.** `PermissionGrant` із `capability` і `scope` (SELF / SUBORDINATES / OWN_DEPARTMENT / OWN_OBJECT / OWN_SUBTREE / COMPANY). Функціональні ролі (бухгалтер, оператор 1С, ревізор) не входять у рівневу ієрархію — їхні повноваження задаються окремо.

5. **Навчання рахується по компетенціях, не по трекам.** `дельта = компетенції посади − чинні компетенції людини`. З цієї формули випливають повторний найм, переведення й підвищення кваліфікації. Кожна компетенція має власний строк дії.

6. **Процеси конфігуровані, не зашиті.** Онбординг, звільнення й переведення описуються шаблонами `ProcessTemplate` + `ChecklistItemTemplate`. Шаблони версіонуються: `ProcessInstance` прив'язаний до версії, редагування шаблона створює нову версію й не ламає активні процеси.

7. **Статус — наслідок процесу.** Ручна зміна статусу працівника заборонена всім, включно з системним адміністратором.

8. **Оцінювання має три шари видимості.** Оперативні позитив/негатив — тільки керівникам. Бейджі й номінації — публічні. Квартальна оцінка — працівнику після бесіди. Працівник ніколи не бачить свій числовий бал. Публічних рейтингових таблиць у системі немає.

9. **Персональні дані.** Скани документів завантажуються тільки через веб на локальний диск, ніколи через бот. Доступ до них — бухгалтерія і керівництво. Системний адміністратор доступу до сканів не має.

## Команди

```powershell
npx dotenv -e .env -- npx next dev        # dev-сервер, порт 3010
npx dotenv -e .env -- npx prisma studio   # перегляд бази
npx prisma migrate dev --name <назва>     # міграція
npm run bot                                # телеграм-бот окремо
```

## Гілки й оновлення бойового сервера

- `master` = те, що працює на бойовому сервері. `dev` = розробка. **Працювати й комітити в `dev`.** У `master` зливати лише за явною вказівкою власника.
- Перед злиттям у `master` обов'язково додати запис зверху `docs/updates.md` (що нового, потрібен бекап?, потрібен seed?, що перевірити). Власник оновлює сервер скриптом `scripts/update.ps1`.
- Міграція, що видаляє чи змінює існуючі колонки, — окремо попередити власника: на живих даних вона необоротна.
- Не запускати seed на бойовій базі без `SEED_MODE=production`; він перезаписує деякі довідники. Деталі — `docs/deployment.md`.

## Чого не робити

- Не використовувати localStorage і sessionStorage. **Єдиний виняток** (рішення власника 2026-10-18): термінал обліку робочого часу зберігає в браузері чергу сканувань, поки немає зв'язку з сервером (VPN), і відправляє її після відновлення.
- Не додавати Docker — на Windows Server 2019 не працює.
- Не додавати Redis — черга на pg-boss поверх PostgreSQL.
- Не приймати фото документів через бот.
- Не показувати працівнику числовий рейтинг і чужі оцінки.
- Не переосмислювати дизайн прототипу без прохання.
- Не робити великий рефакторинг без попередження — я маю розуміти, що змінюється.
